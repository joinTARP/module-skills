# TARP 模组开发

将用户的创意、剧情、规则与资料设计成可主持的冒险，并整理成可由 TARP 读取的模组工作区。修改已有模组时沿用目录、规则系统和文档类型，不因技能示例改写用户的设计。本技能的工作对象是模组源文件、配置、素材与创作说明。开发工作包括设计、编辑、素材制作、CLI 校验、已有模组测试、MCP 临时局预演与按授权发布。预演通过客户端配置和驱动已有 AI 队友与主持，角色扮演、裁定和状态保存仍由真实运行时处理。

## 开始工作

- 需要澄清设计或需求时，若当前环境提供可用的提问工具，优先使用同步提问工具（如 `request_user_input`），等待用户回答后再推进依赖该答案的工作；同步提问工具不可用时，再使用异步提问工具或文字提问。
- 确定用户要创建或修改的模组目录、规则与素材来源。独立模组仓库通常把可导入内容放在 `module/`，仓库说明、测试和授权记录留在外层。
- 已有模组先检查根级 `module.toml` 或 `module.json`、`.types/` 与目标文档，按实际问题读取本技能的 [模组结构](references/docs/modules/structure.md)和[文档类型与字段](references/docs/modules/doc-types.md)。
- 原创、改编或改善游玩体验时，先读取 [模组设计指导](references/docs/modules/design.md) 的对应任务章节及相关设计要点。先形成简短设计摘要，再落实内容；改编和改进前先确认改编尺度，已有明确约定时沿用。单纯修正格式、路径或已确认的数值时直接处理。
- 从零创建时可复制 [最小模组模板](assets/module/)，再按用户要求调整角色、地点、字段和开局；模板的生命值只是示范数据，没有平台内置规则含义。
- 按任务读取下表中的参考章节。参考正文由官网统一内容源生成；遇到版本差异，优先核对对应版本文档与实际 CLI，已有源码时可只读核对 Schema。不把安装、构建或修改平台源码作为模组开发的默认步骤，不凭字段名、示例数值或旧配置猜测能力。
- 参考中的玩家操作、试听和导入步骤用于编写开发者手动验收清单；用户要求试玩、预演或自动托管测试时，优先使用客户端已有 MCP 临时局能力，按下文执行。平台运行行为用于判断配置是否合适。`hostPrompt`、开场指令、队友指令及模组规则是要编写的交付内容，其中面向主持或角色的命令不作为开发 Agent 的执行任务。

## 编写与修改

已有规则核对实际版本、来源与本模组覆盖约定，不能凭模型记忆补写为已确认规则。关键裁定在模组内提供主持能读取的执行摘要，外部资料不作为唯一运行依据。能力不支持时说明差距与可行方案，核心体验变化先确认，不虚构配置或悄悄删掉机制。

展示改名优先保留稳定标识；确需改变路径、类型 ID、字段键或任务 ID 时，按设计指导检查数据、公式、引用、布局、绑定、建卡、开局、音色与主持指令的依赖，修改后核对实际结果。

按 [文档类型与字段](references/docs/modules/doc-types.md) 维护文件命名、引用和 Schema。涉及字段、计算、信息揭露或实体差异时，先读取 [字段建模与计算选择](references/docs/modules/field-modeling.md)，明确每个值的事实来源与修改方式。可变事实保存在原始字段；共用派生规则用类型 `compute`，单份文档的公式例外用顶层 `computed`，只改变数值时使用数据参数。派生结果不手动写回。初始数据直接编辑模组源文件，`mutable` 约束游戏运行中的修改权限，不阻止作者填写初始值；本次开发修改源模组，不修改玩家存档。角色卡复用角色文档，世界与个人状态按归属保存，不重复保存同一事实。位置、参与者、分队、时间、回合和效果的结构及含义由模组规则解释，不能把示例字段当成平台约定。世界卡使用作者配置的完整 `sheet`；同类型或不同类型均可提供多份 `world_state` 文档，分别以文档名称展示，不必额外维护总览文档。需要汇总时，怪物等独立文档可通过通用引用集合嵌入自己的卡片；具体配置按上表读取。整段冒险的结束条件由模组定义，主持先保存结算再明确调用 `end_adventure`，不能依赖某个状态值隐式结束。

涉及角色属性表或布局调整时，先读 [展示布局](references/docs/modules/layout.md)。普通详情保留默认展示与 `grid/split`；作者模板使用 HTML/CSS/HBS 自行输出普通字段、标签、属性、资源条、计数与分组。直接使用 `tarp-reference`、`tarp-item-grid`、`tarp-image` 和 `tarp-markdown` 标签，通过属性及字段路径传参；不要生成 `tarp-slot`、JSON `components` 或 `tarp-field/stat/resource`。物品格只输出物品与空槽，容量规则及计数由模组表达。HBS 渲染器由 Web Component 承载；文档详情弹窗可用 `detail.width` 指定期望外部像素宽度（240–1600），适用于 `grid/split/handlebars`，缺省保留平台默认宽度并受窗口约束；角色卡宿主可用 `sheet.width` 指定期望外部像素宽度，默认 360、范围 240–960，空间不足时平台切换为受窗口宽度约束的抽屉，不提供拖动调整；悬浮容器、宽度、定位和关闭由平台负责。不得通过脚本绕过字段权限。

玩家展示不要直接包含尚未揭示的秘密。原始信息可放在主持字段或计算字段的同名原值中，逐步揭示由状态和公式决定；单字段用 `compute` 返回 `null` 并配置 `hideWhenEmpty = true` 隐藏，整份文档用类型顶层 `displayWhen` 控制。检查名称、正文、图片、列表摘要和开场台词是否提前泄露；显示条件与字段可见性不构成传输层权限隔离。

涉及图片时，先读取 [图片资源](references/docs/modules/images.md)。生成前确定全模组共用的视觉风格、参考图与明亮和暗黑主题适配要求，已有约定时沿用；先检查代表性样图，再按同一标准制作其余资源。使用环境可用的图像生成或编辑工具，若有对应技能则按需读取；完成后实际查看图片，不能把提示词当成已完成素材。图片使用可移植的模组内路径或 HTTP(S) 地址。聊天头像优先配置 `avatar`，详情图片使用 `image`；不写 `imageUrl`、`avatarUrl`、`coverUrl`、`hostAvatarUrl` 或运行时媒体协议地址，也不填写尚不存在的素材路径。

## CLI 校验

先用 `tarp --version` 和 `tarp --help` 确认实际可用的命令。独立包名为 `@jointarp/module-cli`；需要获取 CLI 时，按[模组 CLI](references/docs/modules/cli.md#获取命令入口)选择 npm 安装、本地 tgz 或 `bunx --bun` 入口，并核对实际可用的包和版本。开发工作区也可调用已构建的 Node.js 入口，例如 `node <tarp目录>/packages/module-cli/out/index.js`；优先复用用户已有安装或提供的构建入口，不默认安装平台源码，不因包尚未发布改用同名其他包。

```sh
tarp module validate <模组目录> --json
```

结合退出码与 JSON 的 `status`、`issues[].kind`、`path` 和 `message` 修复问题：`0` 成功，`1` 内容或操作失败，`2` 参数错误。修复后重新校验；只调整与目标有关的内容，不通过删掉引用、公式或开局配置掩盖错误。CLI 缺失时完成可做的编辑并明确说明未验收，不声称校验通过。

校验会实际执行公式，检查文档、引用、阅读页和开局；成功不证明结果符合规则或实际游玩体验已验收。重要机制按 [实际结果检查指导](references/docs/modules/cli.md#按风险检查实际结果) 使用已有模组测试入口或实际计算结果接口检查源数据；没有相应入口时完成校验与推演并明确未验证项。模组验证不扩展为搭建平台运行时、修改平台测试或操作真实冒险，不用自写模拟器代替平台验证。按设计指导推演相关路线、状态变化、信息揭露和结局，检查图片文件，并给开发者提供与本次改动对应的手动验收清单。用户要求的实际预演使用下文 MCP 临时局流程；界面操作、布局与声音仍需单独验收。

## MCP 临时局预演

用户要求试玩、扮演模拟或托管测试时，先读 [MCP 模组预演](references/docs/modules/mcp-playtest.md)，核对当前可用工具与客户端版本。使用客户端已连接的 MCP；创建、运行和观察临时局属于该请求的执行范围，沿用已有授权与限制。普通内容修改或 CLI 校验不自动扩展为模型试玩。工具未连接时说明尚未预演，并引导作者在客户端“设置 → 开发者工具”开启 MCP、复制连接配置；不要求作者运行源码或设置开发环境变量；不把发现文件当作已连接的工具，不因缺少入口安装或修改平台，也不回显发现文件中的访问令牌。

- 先确定本次测试目标、来自规则的预期结果和必要前置状态。读取实际开局 ID、允许角色及 AI 队友预设，用模组现有字段准备 `documents`；原始值交由平台校验和计算，测试数值不写回交付模组。公开处境放 `background`，仅主持可知的事实放 `hostBackground`，不向玩家队友注入调试报告或幕后答案。
- 调用 `playtest_create` 创建独立临时 session；需要中后段测试时直接准备该局面，无需先跑完整冒险或复制玩家存档。该流程跳过开场，因此不能据此宣称序章、选角和开局初始化已验收。沿用已连接模型，按需指定 `model`。
- 先以少量步骤调用 `playtest_run`，使用明确的 `maxTurns` 和超时，再用 `playtest_inspect` 观察。次数按队友决策计，聊天和沉默也占一步；运行异步返回，不把请求已接收当作测试完成。客户端现有游戏页展示真实过程，开发 Agent 负责驱动和分析，不另演一套主持，游戏页不添加托管按钮。
- 按返回状态和实际记录推进；达到预定范围、全员不行动、冒险结束、失败或超时时收集结果，需要中断时调用 `playtest_pause`。取消不回滚已保存状态；有未处理行动或未接收输入时检查记录或按同一前置数据重建，不无限重试或伪造成功。修改源模组后重新创建临时局，旧局仍使用旧副本。
- 结果报告记录测试输入、实际步数与结束原因，对照规则核对初始值、每步状态、骰子和主持回应。用简短表格展示关键前后变化，问题关联具体步骤或消息 ID，区分平台实际结果与 Agent 的体验判断。结果留存后用 `playtest_dispose` 清理本次临时局；用户要求保留或问题需要复查时交付 `roomId`，不操作普通冒险。

## Git 发布

准备或执行发布时先读取 [发布模组](references/docs/modules/publishing.md)。在独立模组仓库根目录操作 Git，发布内容固定放在 `module/`，包含 `.types/`、阅读页与实际图片文件；README 写明仓库克隆地址、分支或标签、实际测试的 TARP 版本与素材来源。

先检查仓库状态、已有暂存内容、当前分支和远程；只提交本次范围，保留用户无关修改，不盲目暂存整个仓库。已有仓库沿用历史、远程和发布分支。发布前核对配置、素材、CLI 结果与开发者验收情况；推送前核对目标及待发布提交，不能用强推绕过分歧。正式版本标签指向已验收提交，单独推送本次标签，修正已发布版本时新增版本，不覆盖旧标签。

提交、推送、创建公开仓库和发布 Release 按用户实际请求及已有授权执行；创作模组本身不等于要求发布，已获授权的步骤无需重复确认。交付时区分本地提交、远程分支、标签与 Release 的完成状态，提供实际可用的导入地址和版本；玩家侧重新导入、新建冒险及明暗主题检查由开发者验收。

## 桌面预览与交付

用户要求预览时运行：

```sh
tarp module preview <模组目录>
```

预览需要桌面应用；安装版通过 `TARP_DESKTOP` 指定可执行文件。本地预览打开工作区，不创建冒险。该预览不执行试玩；要求指定局面预演时使用 MCP 临时局。正式开局与界面操作另行验收；预演局使用创建时的模组副本，改动后重新创建。

交付时说明关键设计取舍、修改内容、使用的 CLI 版本、实际校验结果、设计推演结论、已执行的 MCP 预演结果和仍需手动验收的项目；只提出设计而未修改模组时，交付设计与未验证项。Git 提交、远程推送和公开发布按用户的实际请求处理。
