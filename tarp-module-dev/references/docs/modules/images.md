# 图片资源

图片应帮助玩家辨认人物、理解环境或检查线索。先确定实际用途与可见阶段，再制作素材；不要求每份文档都有图，也不以插画代替必须可查阅的规则和事实。

## 生成前先确定全模组风格

开始生成图片前，先确定一份全模组共用的视觉约定。已有素材或用户指定风格时，先检查并沿用；局部补图应融入现有资源。缺少关键约定时，编程助手优先使用可用的同步提问工具确认，再推进依赖答案的生成工作。批量制作前先完成一张有代表性的样图，检查它是否符合约定，再按同一标准扩展。

视觉约定至少明确：

- 表现方式与时代感，例如写实摄影、手绘水彩或版画，以及服饰、建筑和器物依据。
- 主色、辅助色、明暗范围、光照与材质处理；人物、场景和物品可以有不同构图，但应属于同一视觉体系。
- 人物辨识特征、画面细节密度、镜头和留白方式；同一人物跨图保持脸型、发型、服装与关键配饰一致。
- 明亮和暗黑主题下的背景、边缘与文字处理，以及各类图片的比例和用途。
- 不应出现的内容，例如未揭示身份、秘密出口、额外线索或与时代不符的装饰。

把约定简要记入现有仓库创作说明，方便后续补图沿用。用户已经认可的约定无需每张图重复确认；风格需要改变时，先明确影响范围，不让不同批次各自选择画风。封面、头像、场景图、物品图和地点插画都应遵守共用约定，必要的功能差异应事先说明。

## 同时适配明亮与暗黑模式

同一套图片资源必须在两种主题下都显得协调，内容清楚可辨。不要把软件的当前主题当作模组固定背景，也不要假设图片会随主题自动反色、换底或切换版本；现有图片字段保存一份引用，不能自行添加未经支持的主题专用字段。

| 图片形式             | 制作要求                                                                   | 两种主题都要检查的项目                                           |
| -------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 封面、人物或场景插画 | 优先使用与画面一体的完整背景；避免为了贴合一种主题额外加纯白或纯黑画框     | 边框是否突兀、暗部是否糊成一片、亮部是否刺眼，主体能否辨认       |
| 透明物品图或图标     | 仅在用途需要时使用透明背景；边缘保持干净，并让主体同时区别于浅色和深色底   | 黑色细线是否消失、白色轮廓是否融入背景，有无白边、黑边或裁切残留 |
| 带文字的线索图       | 让文字与图片自身的底色保持足够对比，不依赖软件背景；另提供可阅读的文字资料 | 缩略图与放大后是否清楚，文字是否与线索正文一致                   |
| 地点插画             | 用低干扰的底色和细节表达地点氛围，空间规则由文档说明                       | 主体、文字与关键线索能否看清                                     |

完整插画不必因暗黑模式就改成全黑，也不必因明亮模式就改成全白。应在统一风格内控制背景与主体的对比；透明主体无法兼顾两种底色时，可改为带底的图或调整边缘处理，不把整幅图简单反色作为适配方案。

制作阶段可把图片分别放在浅色与深色背景上比较，检查透明边缘和缩小后的主体；这只是素材检查。最终由开发者在软件两种主题中查看实际显示，包含头像裁切、详情、悬浮预览和图片展示，静态对比不能代替实际界面验收。

## 按用途选择图片

| 用途                   | 配置位置                                               | 制作与信息要求                                                     |
| ---------------------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| 模组封面               | 模组配置的 `cover`                                     | 表达主题与氛围，缩略图仍能辨认；不暴露谜底或结局                   |
| 主持头像               | 模组配置的 `host.avatar`                               | 使用稳定的主持形象；与人物头像区分                                 |
| 人物聊天头像           | 人物文档的 `avatar`                                    | 优先准备方形构图，主体居中，留出圆形裁切空间；不依赖细字或边角装饰 |
| 人物、地点、物品详情图 | 文档的 `image`                                         | 体现当前可见外观，正文承担规则与精确信息；头像与完整插画可分别制作 |
| 信件、照片、图案等线索 | 已公开正文中的 Markdown 图片，或独立线索文档的 `image` | 只展示已经取得的信息；重要文字另有可读正文，图案与调查判定一致     |

图片字段的完整说明见[模组结构](structure.md)和[文档类型与字段](doc-types.md)。聊天头像优先使用 `avatar`，缺少或无法解析时回退到 `image`；不要依靠回退掩盖遗漏或损坏的头像文件。

空间关系和规则信息用模组文档说明，插画作为普通图片资源展示。

### 成品分辨率建议

下表是制作和压缩后的常用尺寸示例，**不是平台强制规格**，也不是图片生成工具的参数要求。先确定布局比例与构图，再选择像素尺寸；高分辨率源稿可以更大，交付时等比缩小。

| 用途                       | 比例与成品尺寸示例                    | 检查重点                                                       |
| -------------------------- | ------------------------------------- | -------------------------------------------------------------- |
| 聊天头像                   | 1:1，512×512 或 768×768               | 小尺寸下脸部可辨，预留圆形裁切空间                             |
| 方形人物立绘、怪物与物品图 | 1:1，1024×1024 或 1536×1536           | 人物与关键道具突出，透明边缘干净；不必让整个人物缩小到完整露脚 |
| 竖幅人物主图               | 4:5，1024×1280；或 2:3，1024×1536     | 发型、服装和姿态在卡片与详情中均能辨认                         |
| 场景、封面和横向原画       | 3:2，1536×1024；或 16:9，1536×864     | 环境结构清楚，缩略图不丢失主体                                 |
| 文字、符号等精细线索       | 按内容决定，必要时长边 1536–2048 像素 | 放大后细节可读，正文另提供可阅读文字，重要标记保持准确         |

地点插画按实际展示与放大需求确定尺寸。较小的物品图也可以足够清楚；选择更高分辨率应有实际展示或放大需求，不为凑尺寸放大低清图片。

## 选择来源与制作方式

先检查用户提供的素材与仓库现有资源，确认用途和已有授权范围，再决定复用、裁切或新增。第三方资源应记录来源页面、作者和实际使用条件；找到搜索缩略图或可下载的文件，不代表已获得再分发许可。按[发布模组](publishing.md)在仓库说明中分别记录素材条件，不把模组代码或文字的许可证自动套用于全部图片。

需要原创人物、场景或复杂插画时，使用当前环境可用的图像生成工具；已有图片需要改图时，使用可用的图像编辑工具，并先查看原图。需要保持人物或场景一致时，提供已确认的参考图，不能只靠重复人物名字。简单的连线示意、网格、精确标记或矢量图形可用代码制作；关键文字与标记由确定性排版完成，不依赖生成模型保证准确。

工具不可用时，完成素材规格、提示词与尚缺资源说明；不把提示词、临时预览或未来路径当作已经交付的图片。付费采购、上传到外部图库或发布素材按用户的实际授权处理。

### 保持批次一致的生成说明

每张图使用相同的视觉约定，再补充该图的内容、用途、比例与当前可见信息。例如：

```text
共用风格：按已确定的画法、时代、调色、光照和材质处理，兼顾浅色和深色界面。
参考：已确认的样图；同一人物的外观参考。
用途与构图：人物头像，方形，主体居中，留出圆形裁切空间。
画面内容：玩家当前已知的外貌与服饰。
保持一致：脸型、发型、衣着、关键配饰与人物参考一致。
不要出现：尚未揭示的身份标志、文字、额外人物或秘密线索。
背景与边缘：遵循既定背景方案，在浅色和深色底上均可辨认。
```

生成后应打开图片检查。若图像改变了人物身份、物品数量、房间出口或关键证据，应修正图片，不据此悄悄改写剧情和规则。压缩或缩放之后也要检查线索细节是否仍可辨认。

## 文件组织与引用

交付用图片放进可导入的模组目录，例如 `module/图片/`，按用途分组并使用稳定名称。高分辨率源稿、提示词和创作记录按需要留在仓库外层，不混入游戏文档。示例目录可安排为：

```text
module/
└── 图片/
    ├── 封面.webp
    ├── 头像/
    ├── scene/
    ├── clue/
    └── 地图/
```

图片引用统一使用从模组根目录出发的相对路径，例如 `图片/头像/旅人.webp`；不要依赖文件所在子目录或同名文件的解析回退。使用 `/`，保留真实扩展名与大小写。格式支持 `avif`、`gif`、`jpeg`、`jpg`、`png`、`svg`、`webp`；不能通过改扩展名完成格式转换。

按用途选格式：普通插画可用 WebP 或 JPEG，透明或精细线索可用 PNG 或保留透明的 WebP，简单矢量图可用 SVG。以实际展示和放大阅读所需的清晰度决定分辨率，压缩无用的大文件；这些是制作建议，不是平台强制规格。

优先将允许随模组分发的图片保存为模组内普通文件，便于复制、离线使用与打包。HTTP(S) 图片地址可以使用，但要说明网络与链接失效风险，并检查实际图片响应；不写本机绝对路径、模组外路径、缓存地址或运行时媒体协议地址。不用软链接代替交付素材。图片生成工具返回的临时文件应实际复制或保存到模组内，再填写引用。

只引用已经存在、能够打开的文件。素材未完成时，省略可选图片字段或使用已存在且不会误导的占位图，并明确缺项；不得填写“预计生成”的路径。没有图片时保留可用文字资料，不让关键路线依赖缺失素材。占位图不应被描述为最终资源。

## 图片与秘密揭露

图片、头像、地点插画、正文图片和替代文本分别检查揭露条件。对文档 `image` 隐藏，不会自动隐藏手写在正文里的同一张图；对某个线索文档隐藏，也不会抹除别处的截图或描述。

按状态揭露时，可以由 `image` 或 `avatar` 的公式选择已有版本，或返回 `null` 并配置 `hideWhenEmpty = true`；具体规则见[计算字段](compute.md)。检查公式可能返回的每个本地图片路径，不只检查初始状态。地点插画包含秘密路线时，另行制作只含已知信息的版本，不把视觉遮挡当成资料权限。图中的题字、图注、替代文本和公开称呼也不能提前揭示身份或谜底。

编写主持资料时，图片展示约定应指向当前可见字段中的真实资源，而不是隐藏原值。图片与文字应采用相同的状态依据，防止正文已更新但图片仍暗示旧局势；实际展示由运行时主持完成。

## 检查与交付

编程助手可完成文件与素材检查；实际软件操作由开发者验收。至少核对以下与本次改动有关的事项：

- 引用文件存在、可解码，扩展名、尺寸与透明通道符合用途；交付目录包含图片实际文件。
- 实际查看图片的主体、边缘、文字和剧情细节，比较代表性的封面、头像与场景，确认共用风格一致。
- 在浅色、深色背景及预期缩略尺寸下检查，修正失去对比、裁切残留和明显突兀的背景。
- 检查图片的初始、隐藏与揭露版本，核对文字、头像、地图、图注与替代文本。
- 运行[CLI 校验](cli.md)检查配置与公式；当前 CLI 不验证图片能否解码、远程图片可用性、视觉风格或明暗主题效果，不能据此声称素材已验收。

给开发者的手动清单应包括：用新冒险分别切换明亮和暗黑模式，查看模组封面、人物聊天头像、详情、悬浮预览、正文放大与图片展示；验证秘密揭露前后版本，检查本地图片在复制或打包后仍可使用。外链资源还要检查网络不可用时的表现。

交付时说明哪些图片已经完成、还缺哪些资源、来源记录在哪里，以及静态检查结果和需要开发者验收的项目。不要把仅写好提示词、通过 CLI 或检查一个主题描述成整套图片已经完成。
